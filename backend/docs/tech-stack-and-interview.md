# SupportOps Agent 技术选型与面试问答

## 1. 项目定位

SupportOps Agent 是一个面向电商售后的智能工单诊断平台。项目的核心不是简单调用一次大模型，而是构建一条可控的 Agent 工作流：

```text
客户问题
→ 结构化意图理解
→ 多场景拆分
→ 受控业务查询 / SKU 知识检索
→ Java 确定性规则
→ 证据与 SOP
→ 基于证据生成客服回复
→ 审计、降级和人工协同
```

面试时可以用一句话概括：

> 我把大模型放在最适合它的“自然语言理解和表达”环节，把权限、查询、状态判断和证据链留在后端确定性代码中，从而解决智能客服容易答非所问、编造数据和不可审计的问题。

## 3. 为什么选择模块化单体

当前系统采用模块化单体，而不是一开始拆微服务：

```text
com.example.supportops
├─ infrastructure
└─ module
   ├─ auth
   ├─ ai
   ├─ diagnosis
   ├─ business
   ├─ knowledge
   ├─ portal
   ├─ analytics
   ├─ trace
   └─ integration
```

理由：

- 项目仍处于快速迭代阶段，场景和数据模型变化频繁；
- 工单、订单、证据、会话之间存在较强事务关系；
- 单体更容易本地启动、调试、测试和开源演示；
- 模块边界已经按领域划分，未来可以按业务压力拆出知识检索、模型网关、会话或分析服务。

面试中要避免说“微服务一定更先进”。合理回答是：先根据团队规模、数据一致性、部署复杂度和独立扩缩容需求选择架构。

## 4. 核心设计决策

### 4.1 大模型不直接访问数据库

模型只输出 `ScenarioType`、摘要、业务编号等受限结构。后端根据枚举白名单选择固定查询计划和 Handler。

收益：

- 防止模型生成危险 SQL；
- 防止越权查询其他客户数据；
- 查询性能与索引可预测；
- 业务规则可测试；
- 每条结论可以追溯到证据。

代价：新增场景需要增加枚举、查询计划、Handler 和测试，开发成本高于完全自由的 Tool Calling，但更适合订单、退款和售后等高准确性业务。

### 4.2 两阶段模型调用

一次正常任务包含：

1. `UNDERSTANDING`：把自然语言转换为 `TicketIntent`；
2. `CUSTOMER_REPLY`：把验证事实转换为对客回复。

业务查询和规则执行位于两次模型调用之间，模型不能绕过事实层。

### 4.3 策略模式处理场景

每个 `ScenarioType` 对应一个 `ScenarioDiagnosisHandler`，启动时构建 `EnumMap` 注册表：

- O(1) 查找；
- 重复 Handler 在启动时立即失败；
- `UNKNOWN` 没有 Handler，避免运行时猜测；
- 新增场景遵守开闭原则。

### 4.4 异步诊断与轮询

创建诊断时立即返回任务 ID，后台线程池执行理解、查询、规则和回复，前端每 800 ms 轮询。

适用原因：模型调用通常需要数秒到数十秒，阻塞 HTTP 请求容易造成网关超时和差的用户体验。

当前轮询实现简单、易调试。生产环境可升级为 SSE、WebSocket 或消息队列回调。

### 4.5 证据优先

Handler 输出不仅包含结论，还包含 `DiagnosisEvidence`：

- 来源记录；
- 字段；
- 对客标签和值；
- 说明；
- 置信度。

回复模型只接收脱敏后的证据值。这样可以在 UI 中解释“为什么得出这个答案”，并为客服审核、审计和模型评测提供依据。

### 4.6 安全降级

模型不是核心业务事实的唯一来源：

- 意图模型失败时使用关键词和可信 hint；
- 回复模型失败时使用规则引擎事实模板；
- 结构化 JSON 失败时只纠错重试一次；
- 额度耗尽时实例级熔断；
- 任务以 `DEGRADED_SUCCESS` 标记，而不是伪装成正常模型成功。

## 5. Java 与 Spring 技术点

### Java 21

- `record` 表达不可变 DTO、VO 和查询快照；
- Switch Expression 对场景枚举进行穷尽路由；
- Text Block 编写 SQL 和纠错上下文；
- `try-with-resources` 管理模型调用审计上下文；
- `List.copyOf`、`Map.copyOf` 冻结只读数据。

### Spring Boot

- Profile 区分 `mock`、`real` 和 `prod`；
- `@ConditionalOnProperty` 切换真实 AI Service 和 Mock 实现；
- `@PreAuthorize` 实现管理员、客服、客户接口权限；
- `@Transactional` 保证注册绑定、附件与片段写入等原子性；
- Bean Validation 校验 HTTP 输入和模型结构化输出；
- `TaskExecutor` 执行后台诊断。

### MyBatis-Plus 与 JdbcTemplate

项目没有为了“技术栈统一”强制所有 SQL 使用一种方式：

- 用户 Mapper 等简单 CRUD 使用 MyBatis 注解；
- 门户聚合、证据、报表和多表查询使用 JdbcTemplate 与显式 SQL；
- 显式 SQL 便于审计查询范围和性能。

生产项目也可以统一迁移到 MyBatis XML、JOOQ 或 Spring Data，但应根据复杂查询、类型安全和团队经验做选择。

## 6. 数据库设计要点

### 核心表类别

- 身份：`support_users`、`customers`、`customer_accounts`；
- 业务事实：订单、支付、退款、物流、优惠券、会员、发票；
- 工单诊断：任务、步骤、报告、证据、模型调用日志；
- 产品知识：文档与片段；
- 客服协同：会话、消息、附件、归档状态；
- SOP 与审计日志。

### 数据完整性

- 唯一索引保证订单号、工单号、会话号和文档哈希唯一；
- 外键维护用户、客户、订单、文档与片段关系；
- Check Constraint 限制状态、角色、文件大小和模型调用次数；
- `ON DELETE CASCADE` 清理文档片段；
- `utf8mb4` 支持完整中文和 Emoji；
- 时间统一使用毫秒精度并配置 Asia/Shanghai。

### 为什么业务状态不能只靠 Prompt

订单状态、退款状态和会话状态属于有限状态机。合法迁移应由 Java 与数据库约束控制，而不是让模型输出一个字符串后直接写库。Prompt 只能解释状态，不能决定数据库是否允许迁移。

## 7. 前端技术点

### Vue 3 + Vite

- Vue 单文件组件承载三角色工作台；
- Vue Router 路由守卫检查 JWT 和角色；
- Vite 本地代理 `/api` 到 Spring Boot；
- 请求层统一处理 401、错误响应和请求追踪号；
- JWT 放在 `sessionStorage`，关闭标签页后失效，降低长期驻留风险。

项目没有引入复杂状态管理库，因为当前跨页共享状态有限。若后续增加多标签客服工作台、实时消息和复杂缓存，可引入 Pinia 与 TanStack Query/Vue Query。

## 8. 高频面试问题与回答要点

### 1. 这个项目和普通 ChatBot 有什么区别？

回答要点：

- 普通 ChatBot 常把问题直接交给模型；
- 本项目先做结构化意图理解，再由后端查询真实数据并执行规则；
- 最终回复必须基于证据；
- 支持审计、降级、权限和人工接管，是业务系统而非聊天 Demo。

### 2. 为什么不让大模型直接生成 SQL？

回答要点：

- 存在 SQL 注入、越权和全表扫描风险；
- 数据库结构变化会让 Prompt 脆弱；
- 退款、订单等高风险业务需要确定性边界；
- 使用场景枚举和固定查询计划可以测试和审计。

### 3. 你们的 RAG 是不是向量检索？

回答要诚实：

- 当前是按 SKU 过滤后的轻量词项检索 RAG；
- 中文二元词和 ASCII 词项做应用层评分；
- MySQL Full-Text 索引已预留，但还未接入 Embedding/向量库；
- 下一步会做 BM25 + Vector + Reranker 的混合检索。

### 4. 为什么 RAG 要先按 SKU 过滤？

回答要点：

- 产品参数具有强实体边界；
- 全库语义相似可能召回其他型号；
- SKU 是高精度元数据过滤条件；
- 先过滤再排序能降低计算量和串货幻觉。

### 5. 为什么分块是 700 字、重叠 100 字？

回答要点：

- 需要在上下文完整性与检索精度之间折中；
- 700 字可以容纳一段规格或一个操作章节；
- 100 字重叠防止步骤和条件在边界处丢失；
- 这是初始经验值，生产环境应通过 Recall@K 和回答正确率调优。

### 6. 如何避免模型答非所问？

回答要点：

- 工单理解 Prompt 强制拆分多需求；
- `scenarioTypes` 按原文顺序保留所有意图；
- 每个意图独立查询和执行 Handler；
- 合并结果后，回复 Prompt 再做一次完整性检查；
- 测试覆盖“价格和物流”等复合输入。

### 7. 如何减少幻觉？

回答要点：

- 模型不直接访问任意工具；
- 只把验证证据交给回复模型；
- 产品资料未命中时明确拒答；
- 规则结论由 Java 生成；
- 数字、状态、地点和时间必须能在证据中找到；
- 保存证据链便于人工复核。

### 8. Prompt 和 RAG 的区别是什么？

回答要点：

- Prompt 定义角色、任务、边界和输出格式；
- RAG 在运行时检索与当前问题相关的外部知识；
- Prompt 不应该存放大量会变化的产品数据；
- RAG 不能替代规则和权限控制。

### 9. 外部模型返回非法 JSON 怎么处理？

回答要点：

- LangChain4j 将响应转换为 Java Record；
- Bean Validation 做二次校验；
- 只对 `AI_RESPONSE_PARSE_FAILED` 执行一次严格格式纠错；
- 其他错误不盲目重试；
- 仍失败则使用规则安全回复并记录降级；
- 曾经发现 600-token 上限截断 JSON，已提高到 1200 并保留重试兜底。

### 10. 为什么模型调用次数限制为 3？

回答要点：

- 正常链路是理解一次、回复一次；
- 第三次只保留给回复格式纠错；
- 数据库约束和应用配置同时限制；
- 防止递归 Agent、成本失控和无限重试。

### 11. 限流和并发如何控制？

回答要点：

- 用户每日额度；
- 每分钟诊断数限制；
- 单账号并发诊断限制；
- 后台线程池与有界队列；
- 单任务模型调用预算；
- 供应商额度耗尽后实例级熔断。

### 12. 为什么创建诊断要支持幂等键？

回答要点：

- 前端重试、网络超时和用户连点可能重复创建任务；
- `requested_by + idempotency_key` 唯一；
- 重复请求复用原任务，避免重复扣额度和重复调用模型。

### 13. 为什么使用轮询而不是 WebSocket？

回答要点：

- 当前任务状态变化频率低，轮询实现简单、故障边界清晰；
- 800 ms 延迟对诊断页面可接受；
- WebSocket 需要连接管理、网关支持和断线重连；
- 生产规模增大时可改为 SSE 或事件推送。

### 14. 如何保证客户只能看自己的数据？

回答要点：

- JWT 包含用户名和角色；
- Controller/Service 检查角色；
- `customer_accounts` 绑定用户和客户实体；
- DAO 查询始终带 `customer_id` 条件；
- 客服与管理员使用不同接口前缀和模块白名单。

### 15. 为什么公开注册只能创建客户？

回答要点：

- 客服拥有查看客户工单和订单的更高权限；
- 若公开注册可指定角色会造成权限提升；
- 注册 SQL 在服务端固定写入 `CUSTOMER`；
- 客服只能由管理员人员管理接口创建。

### 16. 如何设计人工与智能体切换？

回答要点：

- 会话保存 `service_mode`；
- 转人工时不自动发送输入框草稿；
- 客户消息、附件和相关订单独立持久化；
- 只有存在有效 AI 诊断来源时客服侧才展示智能建议；
- 返回智能体后保留原会话上下文，之后仍可再次转人工。

### 17. 消息撤回为什么限制 1 分钟？

回答要点：

- 平衡客户纠错与客服审计；
- 服务端根据发送时间、发送人和会话归属校验；
- 撤回是状态更新或占位文案，不应只在前端隐藏；
- 客服列表摘要也要显示一致的“该消息已撤回”。

### 18. ERP 文件同步如何保证幂等？

回答要点：

- 外部文档使用 `sourceReference` 标识来源；
- 内容使用 SHA-256；
- 同一 SKU + checksum 建立唯一约束；
- 版本号和同步时间可用于后续版本策略；
- 当前相同内容重复推送会被拒绝，生产版可扩展为 upsert 与版本生效规则。

### 19. 为什么使用 Apache Tika？

回答要点：

- 统一解析多种文件格式；
- 降低为 PDF、Word、TXT 分别维护解析器的成本；
- 但复杂布局、扫描 PDF 和表格仍需 OCR/布局模型补充；
- 解析过程必须设置文件和文本长度限制。

### 20. 如何处理文档 Prompt Injection？

回答要点：

- 文档是数据，不是指令；
- RAG 片段只能进入证据区；
- System Prompt 优先级不可被文档改变；
- 检测“忽略规则、泄露密钥、调用工具”等恶意模式；
- 工具计划在后端固定，附件无法新增工具权限；
- 高风险资料进入人工审核队列。

### 21. 为什么选择 JWT？有什么问题？

回答要点：

- 适合前后端分离和无状态 API；
- 服务端不需要保存 Session；
- 问题是撤销困难、泄露后在有效期内可被使用；
- 生产环境应使用短 Access Token、Refresh Token 轮换、黑名单或令牌版本号；
- 必须配合 HTTPS 和安全存储策略。

### 22. 为什么 JWT 放在 sessionStorage？

回答要点：

- 关闭标签页后自动清理，生命周期比 localStorage 短；
- 仍不能抵御 XSS；
- 生产环境更推荐 HttpOnly、Secure、SameSite Cookie，配合 CSRF 防护；
- 当前方案适合演示项目，但要明确风险。

### 23. 数据库迁移怎么做？

回答要点：

- 当前仓库保留初始化 SQL 和 `sql/migrations` 增量脚本；
- Docker 首次建库执行初始化脚本；
- 生产环境应引入 Flyway 或 Liquibase，记录版本并自动校验；
- 应用配置变更必须同步数据库约束，例如模型调用预算从 2 改为 3 时同步迁移 Check Constraint。

### 24. 如何测试大模型功能？

回答要点：

- 默认 `mock` Profile 使用确定性 AI 替身；
- 单元测试覆盖意图、复合问题、结构化重试和模板降级；
- MockMvc 覆盖鉴权和接口；
- 真实模型使用独立测试账号、模拟订单和诊断调用日志验证；
- 不能只看前端按钮，需要核对数据库状态、证据、模型调用类型和最终响应。

### 25. 当前系统最大的不足是什么？

推荐诚实回答：

- RAG 尚未使用向量检索与 Reranker；
- 文档暂存 MySQL BLOB，不适合大规模附件；
- 异步任务使用本地线程池，实例重启时恢复能力有限；
- 限流与模型额度熔断是单实例状态；
- 前端实时通信仍为轮询；
- 数据库迁移尚未接入 Flyway/Liquibase；
- 缺少系统化离线评测集和线上反馈闭环。

回答不足后要继续说明演进方案，而不是回避。

## 9. 场景题

### 如果诊断量增长 100 倍，如何扩展？

建议回答：

1. 将诊断任务写入 Kafka/RabbitMQ，而不是本地线程池；
2. 独立部署模型网关，集中做限流、缓存、熔断和供应商切换；
3. 将产品知识迁移到对象存储和向量数据库；
4. 诊断 Worker 无状态水平扩容；
5. 使用 Redis 做分布式幂等、速率限制和任务状态缓存；
6. 通过 SSE 推送任务进度；
7. 把分析查询迁移到只读库或 OLAP 系统；
8. 增加 OpenTelemetry、Prometheus 和链路追踪。

### 如果模型供应商不可用怎么办？

建议回答：

- 模型网关配置超时、有限重试和熔断；
- 主备供应商切换；
- 意图分类走关键词/轻量本地模型；
- 规则 Handler 继续查询事实；
- 回复走安全模板；
- 报告标记降级并告警，不伪装成正常成功。

### 如果两个产品文档版本冲突怎么办？

建议回答：

- 召回前按版本、生效时间、地区和渠道过滤；
- 无法确定权威版本时把冲突作为证据返回；
- 回复模型明确说明资料冲突并请求人工核验；
- 不让模型自行挑选更“合理”的版本。

## 10. 项目讲解模板

### 30 秒版本

> 这是一个电商售后智能工单平台，使用 Vue 3 和 Spring Boot 构建。大模型先把客户问题拆成一个或多个结构化场景，后端再查询订单、支付、物流或 SKU 产品资料，并通过 Java 策略 Handler 生成结论和证据。最后大模型只能根据脱敏证据生成回复。系统支持三角色权限、人工切换、RAG、异步任务、审计和安全降级。

### 2 分钟版本

建议按以下顺序：

1. **业务痛点**：固定话术答非所问，模型容易编造业务状态；
2. **架构方案**：两阶段 LLM + 中间确定性查询和规则；
3. **关键能力**：多意图、RAG、证据链、三角色、人工接管；
4. **技术难点**：结构化输出、数据权限、异步编排、降级；
5. **真实问题**：600-token 截断 JSON、应用预算与数据库约束不一致；
6. **修复方式**：提高输出预算、仅解析失败纠错重试、同步迁移数据库约束、增加回归测试；
7. **下一步**：混合向量检索、消息队列、对象存储和评测平台。
